# Security Audit: jeb-slim (Pubky mention-reply bot)

Scope: `src/*.ts` (18 files), `Dockerfile`, `docker-compose.yml`, `.env.example`, `.dockerignore`, `.gitignore`, `scripts/test-pg.sh`, git tracking state. Read-only; no files modified, no builds run, no secret values accessed.

## Findings table

| ID | Severity | File:line | Issue | Fix |
|---|---|---|---|---|
| F-01 | Medium | `homeserver.ts:70-80`, `bot.ts:41-46` | Session created once at startup; **no session-expiry detection or re-auth**. If the homeserver session expires/revokes, every publish fails forever; mentions churn `failed`→`processing`→`failed` (bot.ts:137-138) with no recovery or alarm. | Detect 401/403 from `putJson`, tear down and re-run `openTransport` with backoff; surface `lastPollAt`-style staleness on `/healthz`. |
| F-02 | Medium | `bot.ts:127` vs `bot.ts:197` | **Kill switch is checked before the model call, not before the write.** A publish can land `modelDelayMs` + up to `modelTimeoutMs` (default 30 s) after the switch is flipped on. | Re-check `killSwitchOn()`/`disabledEnv` immediately before `publishReply` (bot.ts:197). |
| F-03 | Medium | `bot.ts:169`, `nexus.ts:39-54` | **Per-thread cap is keyed on attacker-controlled data.** `root` is the tail of a chain built from `relationships.replied` in Nexus JSON. An attacker who chains their own posts (or a chain > 25, hitting the walk cap mid-thread) gets a fresh "root" per mention and evades `maxRepliesPerThread` (default 1). Only the per-author hourly cap (F-04's 5/hr) bounds this. | Treat the cap as best-effort; document it; consider also capping per (author, root) or globally per hour; consider trusting only Nexus-verified thread roots. |
| F-04 | Medium | `bot.ts:98-101`, `nexus.ts:10,25,33` | **Unbounded concurrency + no fetch timeouts.** Every notification spawns `void this.consume(...)`; each consume performs up to ~50 sequential `fetch()` calls (25 ancestors + 25 userDetails) with no `AbortSignal`/timeout. A flood of mentions (or a slow/malicious Nexus) → unbounded in-flight promises, hung sockets, memory growth. | Add per-fetch timeouts (AbortController), cap concurrent consumes (semaphore), bound total chain-fetch time. |
| F-05 | Medium | `docker-compose.yml:5-7,23` | Hardcoded `POSTGRES_PASSWORD: postgres`, `DATABASE_URL` with the same credential, and Postgres published on host `0.0.0.0:5432`. Fine for local dev; dangerous if this compose file reaches staging as-is. | Use env-injected password, drop the host port mapping (or bind `127.0.0.1`), mark compose as dev-only and provide a staging overlay. |
| F-06 | Medium | `log.ts:5-8` | Pino redact list covers only 4 exact top-level paths. `signupToken`, `databaseUrl` (embeds DB password), `modelApiKey`, and nested keys (e.g. `cfg.*`, `err.config.*`) are **not** redacted. `lg.info({ err: String(e) })` (bot.ts:193,201) is safe only as long as SDK errors stringify without secrets — an assumption, not a guarantee. | Use wildcard redact paths (`*.secretKeyHex`, `*.signupToken`, `*.databaseUrl`, `*.modelApiKey`, `cfg.*`); never log config/session objects. |
| F-07 | Low | `config.ts:38` vs `README.md:9-10`, `keygen.ts` | README implies keygen-file workflow, but **nothing ever reads the key file** — only `JEB_SLIM_SECRET_KEY_HEX` is loaded. Users must manually copy the hex into env; the on-disk key file (secrets/bot.key, currently present) is orphaned attack surface. | Either add a `JEB_SLIM_SECRET_KEY_FILE` loader (read at boot, 0600 check) or fix README; delete the unused file. |
| F-08 | Low | `keygen.ts:20-25` | Write stream has **no `error` handler**; on write failure the process can still print the pubkey with exit 0 beside an empty/partial key file. No fsync. | Handle `error`, exit non-zero on failure, fsync before printing pubkey. |
| F-09 | Low | `context.ts:17-23`, `bot.ts:161-166` | Prompt assembly interpolates raw attacker post content and profile names with **no length cap** (chain of up to 25 posts). Token/cost amplification and easier prompt-injection payload delivery against the LLM path. | Truncate each post's content (e.g. 500 chars) and total prompt size; keep prompt-injection caveat documented (bot will publish model output under its identity — inherent, but should be stated). |
| F-10 | Low | `nexus.ts:31-32` | `userDetails(id)` interpolates `p.details.author` from Nexus JSON into the URL path **without validation** (unlike `post()`, which uses strict `parsePostUri`). Host is fixed so no SSRF, but malformed ids produce path garbage; trust boundary undocumented. | Validate author ids against `^[a-z0-9]{52}$` before fetch. |
| F-11 | Low | `bot.ts:100`, `db.ts:9` | Whole design **trusts Nexus absolutely**: a compromised Nexus feeds arbitrary authors/URIs/parent chains/content into the prompt and policy keys. Fail-closed on Postgres (verified: `killSwitchOn()` throw → catch → skip; `ping()` gate in consume) but fail-open toward Nexus data integrity. | Document the trust assumption; pin `JEB_SLIM_NEXUS_URL`; consider response-size limits on `res.json()`. |
| F-12 | Low | `health.ts:17`, `docker-compose.yml:24-25` | `/healthz` binds `0.0.0.0` and is published on host `8787`. Leaks only `lastPollAgeMs` — low impact, but it's an unauthenticated network surface with no need to be public. | Bind `127.0.0.1` by default or don't publish the port in compose. |
| F-13 | Low | `docker-compose.yml:21-23` | Secrets via `env_file` + `environment` are visible in `docker inspect` and `/proc/<pid>/environ` to any docker-socket user. No `read_only`, no `cap_drop`, no `restart` policy. Base image unpinned by digest (`Dockerfile:1,9`). | Docker secrets or mounted key file for the signing key; add hardening flags for staging; pin image digests. |
| F-14 | Low | `contract-adapter.ts:26-31` | Adapter disables/weakens policy for the harness (`maxPerUserPerHour: 10_000`, empty blocklist, `pollMs: 40`) and bypasses the 64-hex env validation (only `openTransport`'s 32-byte check remains). Acceptable for tests, but nothing prevents pointing it at production Nexus/homeserver. | Add a guard comment/assert (e.g. refuse non-testnet unless `ALLOW` flag) so the weak-policy path can't be driven at mainnet by accident. |

**Checked and OK (no finding):** all SQL parameterized incl. the `$1::text || ' milliseconds'` interval trick (db.ts:128); `parsePostUri` strict regex gates the PUT parent (types.ts:54); no DELETE or profile write exists in the codebase; content hard-sliced to 2000 chars in both model.ts:27 and homeserver.ts:87; publish path is library-derived under the bot's own posts prefix — attacker text cannot influence `meta.path`; keygen file mode 0600; `secrets/` and `.env` gitignored and dockerignored; **no git remote configured and no secrets tracked in git**; Dockerfile is multi-stage, pruned, non-root (`USER jeb`); health endpoint carries no secret data; logs never print post bodies or key material (only public URIs/pks); kill-switch fail-closed on Postgres outage.

## Per-question notes

1. **Key material.** Env-only load path (`config.ts:38-39`, validated 32-byte hex, lowercased). Held for process lifetime in `Config` and as `Buffer`/`Keypair` in `openTransport` — never zeroed (acceptable for a long-lived signer, but worth noting). Not reachable from `/healthz`, logs are clean today but redaction is shallow (F-06). Keygen writes 0600 but with fragile stream handling (F-08); the key-file workflow is half-implemented (F-07). Nothing serializes the session; `contract-adapter` passes the secret through an env object (harness trust).
2. **Session/auth.** Signin → (on *any* error) signup-with-token → (on error) signin retry (`homeserver.ts:70-80`). Two concerns beyond F-01: a transient network error triggers a signup attempt (may burn a one-time token), and errors are swallowed (`catch {}`) so the real failure reason is lost. `signupToken` lives in memory forever.
3. **Publish authorization.** PUT path cannot be influenced by mention content, Nexus JSON, or LLM output — `PubkySpecsBuilder.createPost` derives it; parent is regex-validated; no DELETE/profile code exists; 2000-char cap enforced twice. Minor: `kind` is chosen from pre-slice length (`homeserver.ts:86-87`), so >2000-char model output yields a `Long`-kind post with ≤2000 chars — cosmetic. Root cause of cap evasion is F-03.
4. **Untrusted data.** SQL fully parameterized. **No SSRF**: all fetch hosts come from operator config (`nexusUrl`) or the SDK; attacker data only affects paths, and the riskiest path input (`post_uri`/`parent`) is strictly validated — except `userDetails` (F-10). Prompt assembly is raw interpolation (F-09). No command execution or filesystem paths built from attacker text anywhere.
5. **Policy.** Kill switch gates the only write path but with a stale-check window (F-02). Thread cap forgeable (F-03). Per-user hourly limit is keyed on Nexus-supplied author and is the real backstop (5/hr default). Blocklist is exact-match on the Nexus-supplied pubkey — sound given honest Nexus. Postgres-down behavior verified fail-closed in both `pollOnce` and `consume` (kill-switch throw → catch → skip; ping gate).
6. **Privacy/logging.** No content bodies, no secrets, no stack traces (`String(e)` only) in logs; mention keys and reply URIs are public data. Weakness is the redaction list's narrowness (F-06) and reliance on SDK error strings never containing secrets.
7. **Docker/compose.** Good bones: multi-stage, non-root, `.dockerignore` excludes `.env`/`secrets`, `npm ci`. Gaps: dev-grade Postgres creds + host port exposure (F-05), secret-in-env visibility (F-13), health port published (F-12), unpinned base image.

## Verdict: **FIX-FIRST**

No Critical findings — the signing key is well-contained, publish authorization is structurally sound, and the database layer is clean. But five Mediums should block staging with a real funded identity:

**Blocking: F-01** (no session re-auth — the bot silently dies as a signer), **F-02** (kill switch must gate the actual write), **F-03** (thread cap is attacker-evadable; at minimum document and add a global hourly backstop), **F-04** (unbounded concurrency/no timeouts — remote-triggered resource exhaustion), **F-05** (strip dev credentials/ports before any non-local deploy).

F-06 through F-15 can ship to staging but should land before production.
